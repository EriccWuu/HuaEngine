## 1. 概述

本规范定义 HuaEngine 下一阶段的目标: 让 `Editor` 从“固定 workbench 壳”演进为“可创建工程、打开工程、编辑工程并保存结果”的最小闭环项目工作台。

当前阶段不追求完整商业化体验，不要求一次性补齐模板市场、导入流水线、完整资源浏览器或高级多文档 UX。当前只要求建立一个真实可用的最小闭环，让引擎可以围绕正式工程目录工作，而不是继续依赖写死的临时 workbench 路径。

**目标用户**:
- 引擎维护者
- 使用 Editor 的内容开发者
- 需要通过 GUI 验证项目、场景、资产闭环的开发者

**成功指标**:
- Editor 可以创建或打开任意 HuaEngine 工程，而不是只能使用固定 `%LOCALAPPDATA%/HuaEngine/Workbench`
- Editor 启动后能明确知道“当前工程”和“当前场景文档”
- 用户可以完成 `创建工程 -> 打开工程 -> 创建/加载场景 -> 编辑 -> 保存 -> 下次重新打开恢复`
- 项目、场景、资产和验证结果在同一工作台上下文中闭环

## 2. 问题陈述

### 2.1 当前状态

HuaEngine 已经具备正式的 `ProjectService`、`SceneService`、`AssetService`、`ApplicationOperations` 和基础 Editor 工作台外壳。但当前 Editor 仍然围绕固定的本地 workbench 项目启动，缺少真正的“项目级”操作体验:

- 不能在启动时显式创建或打开任意工程
- 当前场景文档缺少明确的文档状态边界
- 没有正式的工程浏览入口和最小资产工作区
- 工程级操作和场景级操作没有形成完整用户闭环

### 2.2 痛点

- 引擎底层已支持项目上下文，但 Editor 仍然不能像正式引擎一样围绕任意工程工作
- 当前 workbench 更像内部演示壳，不像真正的项目工作台
- 工程、场景、资产和诊断在 GUI 中仍然缺少统一的项目会话模型
- 对用户而言，引擎“能不能真正拿来用”取决于是否存在完整工程工作流，而不只是服务层 API

### 2.3 期望结果

形成一套新的 Editor 最小闭环:

- 可以创建工程
- 可以打开已有工程
- 可以在工程内加载或创建场景
- 可以编辑并保存场景
- 可以在同一工作台内查看项目目录、场景树、Inspector、Console 和基础诊断

## 3. 用户故事

### US-1: 创建新工程

**优先级**: Must

作为引擎用户，
我想在 Editor 中创建一个新的 HuaEngine 工程，
以便我不用手工准备目录结构就能开始使用引擎。

**验收标准**:
- [ ] Editor 提供正式的“创建工程”入口
- [ ] 创建结果是完整工程目录，而不是临时工作目录
- [ ] 创建后 Editor 自动切换到新工程上下文
- [ ] 创建失败时能够显示明确原因和目标路径

### US-2: 打开已有工程

**优先级**: Must

作为引擎用户，
我想打开任意已有 HuaEngine 工程，
以便我能继续编辑已有内容，而不是只能操作固定 workbench。

**验收标准**:
- [ ] Editor 提供正式的“打开工程”入口
- [ ] 打开动作基于 `ProjectService` 正式解析工程上下文
- [ ] 工程打开后，工作台能显示当前工程关键信息
- [ ] 无效工程路径会返回明确诊断而不是静默失败

### US-3: 在工程内编辑并保存场景

**优先级**: Must

作为内容开发者，
我想在当前工程中创建、打开、编辑并保存场景，
以便场景编辑成为正式工程工作流的一部分。

**验收标准**:
- [ ] 工程内可以创建新场景
- [ ] 工程内可以加载已有场景
- [ ] 保存会落到当前工程场景目录
- [ ] 重启 Editor 后可以重新打开之前保存的场景

### US-4: 以项目会话方式消费资产和诊断

**优先级**: Should

作为内容开发者，
我想在工作台里看到当前工程的基础资产视图和诊断结果，
以便我知道当前工程是否可用，以及场景引用的资源来自哪里。

**验收标准**:
- [ ] 工作台存在最小项目/资产浏览视图
- [ ] 工作台能展示当前工程根、资产目录和场景目录
- [ ] 保存或加载后的诊断能在同一会话内回看
- [ ] 当前工程校验结果可在 GUI 中查看

### US-5: 保持最小闭环优先而非过早做重工具链

**优先级**: Must

作为引擎维护者，
我想先建立最小可用闭环，
以便先让引擎能用起来，再继续迭代更高级的编辑器能力。

**验收标准**:
- [ ] 本阶段不要求完整导入流水线、模板市场、复杂文件对话框
- [ ] 本阶段优先保证工程会话、场景文档和保存恢复闭环
- [ ] 本阶段所有新增 GUI 能力都必须建立在既有 `ApplicationOperations` 上

## 4. 功能性需求

| ID | 需求描述 | 优先级 | 关联 US |
|----|----------|--------|---------|
| FR-1 | Editor 必须支持创建新工程并切换到该工程上下文 | Must | US-1 |
| FR-2 | Editor 必须支持打开已有工程并解析正式 `ProjectContext` | Must | US-2 |
| FR-3 | Editor 必须建立“当前工程 + 当前场景文档”的明确运行时模型 | Must | US-2, US-3 |
| FR-4 | Editor 必须支持工程内新建、打开、保存场景 | Must | US-3 |
| FR-5 | GUI 工作台必须展示当前工程的最小项目/资产视图 | Should | US-4 |
| FR-6 | 工程级和场景级诊断必须能在工作台中统一查看 | Should | US-4 |
| FR-7 | GUI 新能力必须通过 `ApplicationOperations` 消费正式能力，而不是直接绕回原始服务 | Must | US-5 |
| FR-8 | 项目会话必须允许下次打开时恢复到正式工程，而不是依赖固定临时 workbench | Must | US-1, US-2, US-3 |

## 5. 非功能性需求

| ID | 类型 | 需求描述 | 验证方法 |
|----|------|----------|----------|
| NFR-1 | 可用性 | 用户在一次 Editor 会话中应能完成 `create/open -> edit -> save -> reopen` 最小闭环 | 手工闭环演练 |
| NFR-2 | 一致性 | GUI 必须继续复用统一 `ResultEnvelope` 和 `ApplicationOperations` 语义 | 代码结构审查 |
| NFR-3 | 可恢复性 | 工程或场景加载失败时，工作台必须停留在可理解状态而不是直接不可用 | 故障路径演练 |
| NFR-4 | 渐进演进 | 本阶段方案应允许后续继续扩展项目浏览器、最近工程、资源导入和多场景文档 | 架构评审 |

## 6. 约束条件与假设

### 6.1 约束条件

| 类型 | 描述 | 来源 |
|------|------|------|
| 现状 | 当前 Editor 仍以单 `EditorLayer` 和固定 workbench 项目路径启动 | 当前代码库 |
| 架构 | 统一公开能力入口已经收敛为 `Application::GetOperations()` | 已批准实现 |
| 边界 | 本阶段重点是建立项目工作台闭环，不扩展完整工具链 | 用户说明 |
| 技术 | 当前主要持久化格式仍为 JSON，项目和场景格式已正式化 | 当前代码库 |

### 6.2 假设

| ID | 假设描述 | 如果错误的风险 | 已验证 |
|----|----------|----------------|--------|
| A-1 | 用户当前优先级是“先能用”，而不是先做复杂 UX | 范围会膨胀 | 是 |
| A-2 | 初期可以接受使用最小路径输入或项目面板，而不是马上接系统文件对话框 | GUI 体验较原始 | 是 |
| A-3 | 资产视图当前只需要最小浏览和场景相关操作，不要求完整导入链 | 资产体验不完整 | 是 |
