# 分析：engine-editor-capability-expansion

## 1. 输入规范结论

已批准规范的核心目标是：在现有项目工作台闭环之上，把 `Editor` 提升为真正可日常使用的基础编辑器，并且为后续高级编辑器能力保留可持续扩展空间。

当前阶段明确要求纳入的基础交互能力包括：

- `Undo / Redo`
- 上下文相关右键菜单
- 内置快捷键与可扩展快捷键体系
- 单选 / 多选
- 拖拽

当前阶段明确要求的第一批优先功能包括：

- `Hierarchy` 右键菜单
- `Hierarchy` 新建实体
- `Hierarchy` 删除选中实体，覆盖单选与多选
- `Inspector` 右键菜单
- `Inspector` 添加组件
- `Inspector` 删除组件

## 2. 现有仓库约束

基于当前代码与模块 Skill，现状约束如下：

- `Editor` 已具备项目工作台闭环，但交互面仍偏轻量
- `Selection` 仍是全局静态单选模型，不支持多选
- `HierarchyPanel` 当前仅做实体枚举与单击选中
- `InspectorPanel` 当前仅消费单选对象并调用 `ComponentEditorRegistry::DrawComponents(...)`
- 当前仓库尚无正式的编辑器命令栈、快捷键注册表、右键菜单归口或拖拽操作层
- GUI 仍需继续走 `ApplicationOperations` / 正式工作台状态面，不能回退成随意直连

## 3. 需要架构决策的关键点

### D-1：编辑器交互能力归口

需要决定 `Undo/Redo`、快捷键、上下文菜单、拖拽和多选这几类交互能力应如何归口，避免继续散落在 `EditorLayer` 与各面板内部。

### D-2：选择模型升级路径

需要决定如何从当前全局单选 `Selection` 升级到支持单选 / 多选 / 批量操作的选择模型，同时不破坏现有 `Inspector` 和 `Hierarchy` 的最小可用性。

### D-3：编辑动作与命令边界

需要决定实体增删、组件增删、拖拽组织、快捷键触发等动作，哪些应进入统一命令体系，哪些保留直接 UI 行为。

### D-4：上下文菜单与快捷键注册面

需要决定右键菜单和快捷键如何形成规范化接入入口，以便未来面板和工具可继续注册新动作。

### D-5：第一批优先功能落点

需要决定 `Hierarchy / Inspector` 首批高频编辑动作如何作为第一批能力切入，同时与后续大范围交互体系兼容。

## 4. 调研主题

### Topic-1：编辑器交互命令骨架

核心问题：

- 如何把 `Undo/Redo`、快捷键触发、菜单动作、批量删除等行为统一收口为可扩展编辑命令面

关注维度：

- 命令对象粒度
- 历史栈边界
- UI 触发到命令执行的归口
- 与现有 `ApplicationOperations` / `SceneDocument` / dirty state 的关系

### Topic-2：选择、多选与批量编辑模型

核心问题：

- 如何把当前单选 `Selection` 升级为可支撑多选、批量删除和 Inspector 兼容行为的选择模型

关注维度：

- 选择状态表示
- 单选与多选兼容
- Hierarchy 交互形态
- Inspector 在多选下的行为退化策略

### Topic-3：上下文菜单、快捷键与拖拽接入面

核心问题：

- 如何为面板提供统一的右键菜单、快捷键和拖拽接入入口，而不是继续在各面板散写逻辑

关注维度：

- 上下文作用域
- 面板注册机制
- 内置动作与未来扩展动作并存
- 第一批优先功能的落地路径

## 5. 计划阶段成功标准

- 形成一份中文 `plan.md`
- 明确编辑器交互骨架、选择模型升级路径、第一批功能落点
- 明确哪些能力属于本阶段要落地，哪些能力只做扩展缝
- 不下沉到具体任务拆分或测试步骤
