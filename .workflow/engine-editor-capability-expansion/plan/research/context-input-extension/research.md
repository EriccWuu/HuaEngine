# 调研：上下文菜单、快捷键与拖拽接入面

## 1. 调研范围

本调研关注三类输入与交互扩展面：

- 上下文右键菜单
- 快捷键
- 拖拽

目标不是一次做完整高级系统，而是建立规范化接入入口。

## 2. 现状判断

当前工作台已经有菜单栏和若干弹窗，但这些行为仍然主要依赖硬编码入口。[E-1]

如果继续沿用这种方式，会导致：

- 新动作只能继续加 `if/else`
- 不同面板各自维护右键菜单逻辑
- 快捷键无法形成统一冲突管理与注册入口
- 拖拽会变成局部面板私有实现，后续难统一

## 3. 方案比较

| 方案 | 描述 | 优点 | 问题 |
|------|------|------|------|
| A | 各面板各写右键菜单、快捷键、拖拽 | 快速 | 扩展性最差，后续维护成本高 |
| B | 只做硬编码的第一批功能，未来再重构 | 短期最省事 | 会把第一批功能做成负债 |
| C | 先建立轻量注册面：上下文菜单注册、快捷键注册、拖拽意图入口，再让第一批功能接入 | 兼顾当前交付与未来扩展 | 需要多一层基础设施 |

## 4. 推荐结论

推荐采用方案 C。[E-1][E-2]

建议本阶段形成的最小接入面应满足：

- 右键菜单按“上下文区域”注册动作
- 快捷键按“命令标识”注册绑定
- 拖拽按“来源 / 目标 / 结果意图”组织

这样第一批功能虽然只落在 `Hierarchy / Inspector`，但接入方式不会把后路堵死。

## 5. 对本次计划的影响

- 本阶段应新增轻量注册式交互层，而不是一次做重型工具框架
- `Hierarchy` / `Inspector` 应成为第一批上下文动作接入点
- 快捷键需要先覆盖核心内置命令，同时保留未来自定义注册槽位
- 拖拽本阶段可以先完成基础意图入口，不必一次做到完整复杂行为
