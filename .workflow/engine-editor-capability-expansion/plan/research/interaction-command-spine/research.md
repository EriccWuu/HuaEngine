# 调研：编辑器交互命令骨架

## 1. 调研范围

本调研只关注 Editor 内部交互能力如何形成统一骨架，以承载：

- `Undo/Redo`
- 快捷键触发
- 上下文菜单动作
- 多选批量删除
- 面板间共享编辑动作

## 2. 现状判断

当前仓库已经具备统一的领域操作面 `ApplicationOperations`，但 Editor 自身仍缺少一层“交互命令骨架”。[E-1][E-2]

表现为：

- 各面板动作仍偏直接执行
- Inspector 编辑只回传“是否改动”
- 缺少统一命令历史栈
- 缺少动作元信息（名称、来源、是否可撤销）

## 3. 方案比较

| 方案 | 描述 | 优点 | 问题 |
|------|------|------|------|
| A | 继续在各面板直接写交互逻辑 | 改动快 | 很快失控，无法支撑撤销重做和统一快捷键 |
| B | 把所有编辑动作都塞进 `ApplicationOperations` | 入口统一 | 混淆领域能力与编辑器交互能力，污染正式操作面 |
| C | 在 Editor 内建立交互命令骨架，并与工作台状态协同 | 既保留领域边界，又能承载撤销/快捷键/菜单/批处理 | 需要新增一层基础设施 |

## 4. 推荐结论

推荐采用方案 C：在 Editor 内建立专门的交互命令骨架。[E-1][E-2]

其职责应包括：

- 统一描述“编辑动作”
- 统一接收菜单、右键、快捷键、拖拽等触发源
- 支撑是否可撤销、是否可批量执行、是否影响 dirty 状态
- 为第一批 `Hierarchy / Inspector` 高频功能提供稳定归口

## 5. 对本次计划的影响

- `Undo/Redo` 不应作为零散附属能力插进去，而应成为交互命令骨架的自然产物
- `Hierarchy` 删除多选实体与 `Inspector` 组件增删都应优先接入同一命令面
- 本阶段无需做完整高级命令系统，但必须把第一版骨架搭出来

## 6. 证据引用

- [E-1] `EditorLayer / HierarchyPanel / InspectorPanel` 当前直接 UI 执行路径
- [E-2] `ApplicationOperations` 已是领域能力归口，但不适合作为编辑器交互层
