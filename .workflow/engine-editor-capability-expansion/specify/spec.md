# 规范：engine-editor-capability-expansion

## 目标

将当前 HuaEngine 编辑器从“仅具备最小闭环的工作台”推进为“足以支撑日常引擎使用的基础编辑器”，在补齐基础能力集合的同时，为未来新增面板、工具、工作流和更丰富的编辑操作保留清晰空间。

## 功能需求

- FR-1：编辑器必须提供更清晰、更完整的项目与场景编辑基础工作台
- FR-2：常用编辑动作必须更容易被发现和完成，不能依赖隐藏流程或脆弱路径
- FR-3：项目、场景、视口、层级、检视器和反馈面必须构成一致的编辑体验
- FR-4：编辑器必须支持超出当前最小壳层的基础日常编辑工作流集合
- FR-5：当前阶段形成的编辑器基础面必须为未来能力扩展保留可见空间，而不是变成死路式 UX
- FR-6：本阶段新增编辑器能力必须继续与已建立的项目工作台方向保持一致

## 非功能需求

- NFR-1：本阶段必须明显提升实际可用性，但不追求一次性补齐完整生产级工具链
- NFR-2：编辑器在当前引擎使用场景下必须保持可理解、可导航
- NFR-3：本阶段形成的基础面必须能支撑未来继续扩展编辑器能力
- NFR-4：本阶段必须保护现有项目工作台闭环，而不是让它回退

## 范围

- 编辑器基础能力基线
- 项目与场景编辑体验完整性
- 面板与视口的可用性预期
- 常用编辑动作的可发现性
- 本阶段“必须具备的编辑器能力集合”的显式定义
- 面向未来扩展的编辑器产品面要求

## 非目标

- 完整生产级内容浏览器
- 高级导入 / 重导入流水线
- 模板市场或插件市场
- 引擎版本管理启动器能力
- 高级多文档创作套件

## 基础能力基线

本规范要求当前阶段至少具备以下编辑器基础能力：

- 支持创建、打开、恢复项目的项目入口
- 工作台内可见的当前项目上下文
- 工作台内可见的当前场景文档上下文
- 可见的场景文档动作：新建、打开、保存、另存为、校验
- 稳定的核心面板集合：项目、层级、检视器、场景视口、控制台
- 贯穿层级、检视器和场景视口的选择驱动编辑闭环
- 对成功、失败、需人工处理、脏状态和校验状态的可见反馈
- 能让编辑器回到有意义工作上下文中的会话连续性

## 延后能力区域

以下能力明确延后到本基础里程碑之后：

- 深度资产浏览器工作流
- 重型资产导入与重导入工具
- 高级内容管理 UX
- 最终形态的启动器生态能力
- 大规模编辑器自定义系统

## 用户故事

### US-1：在完整的基础编辑器中工作

作为编辑器用户，  
我希望编辑器能提供更完整的基础工作台，  
以便我把它当成主要 GUI 宿主来使用，而不是把它视为一个轻量壳层。

验收标准：

- 打开项目后，同一编辑器会话中可见项目上下文、层级、检视器、场景视口和控制台这些工作面。
- 编辑器为本规范定义的基础场景文档动作提供可见入口。
- 无项目时的入口流程提供可见的“创建项目 / 打开项目 / 恢复项目”动作，而不是依赖隐藏 fallback 认知。
- 用户可以仅依靠本规范定义的基础能力集合完成工作，而不需要仓库私有的隐藏步骤。

### US-2：可靠完成常用编辑流程

作为内容创作者，  
我希望常用的项目与场景编辑流程是一致且易发现的，  
以便我能低摩擦地完成日常工作。

验收标准：

- 编辑器提供可见的项目创建 / 打开 / 恢复动作，以及场景新建 / 打开 / 保存 / 另存为 / 校验动作。
- 每个基础动作执行后，界面都会显示成功、失败或需要注意的反馈。
- 产品支持把当前工作台重新恢复到最近一次有意义的项目 / 会话上下文。
- 用户能够不离开编辑器产品面，从项目入口一路完成到场景编辑与保存。

### US-3：清楚理解当前编辑上下文

作为编辑器用户，  
我希望编辑器能明确展示当前项目、当前场景、当前选择对象和当前工作状态，  
以便我能更有把握地进行编辑。

验收标准：

- 工作台在编辑过程中显示当前激活项目标识和当前激活场景标识。
- 工作台显示当前场景是否存在未保存修改。
- 当前选择对象能在层级中被看到，并在检视器编辑面中得到反映。
- 用户在编辑内容时，可以从同一工作台会话中查看诊断反馈和运行时日志反馈。

### US-4：使用一个可以继续成长的基础面

作为引擎维护者，  
我希望基础编辑器体验为未来扩展保留空间，  
以便后续新增能力时不必重做整个编辑器产品形态。

验收标准：

- 本规范定义的基础面，仅要求完成“基础能力基线”章节列出的能力集合。
- 本规范中被延后的高级工具能力，不是本里程碑完成的前提条件。
- 编辑器产品面仍围绕可复用的工作台工作面组织，而不是被压缩成单一用途流程。
- 后续编辑器能力可以在当前基础工作台旁继续扩展，而不是整体替换它。

### US-5：在不过早膨胀工具链范围的前提下提升编辑器

作为引擎所有者，  
我希望这一阶段能真正提升编辑器，而不是把它膨胀成过大的工具链项目，  
以便引擎现在就更可用，同时也保留后续路线图空间。

验收标准：

- 本阶段只要求完成本规范列出的基础能力集合，不要求覆盖延后能力区域。
- 即使高级工具尚未出现，只要编辑器已经能支撑基础项目与场景工作，本里程碑就可以视为完成。
- 本规范明确将更高级的编辑器雄心放在当前里程碑之外。
- 后续规划可以继续在当前范围上扩展，而不需要重定义这条基础线。

| FR-2 | 提供可见的项目创建 / 打开 / 恢复和场景新建 / 打开 / 保存 / 另存为 / 校验动作 | Must | US-2 |

| ID | 类型 | 需求描述 | 验证方式 |

## 约束

- 本规范必须停留在“用户需要什么”的层面，不能落到实现设计。
- 现有项目工作台闭环是基线，不是需要推倒重来的对象。
- 当前阶段是“基础能力扩展”，不是“编辑器最终成熟态”。
- 编辑器应继续作为引擎的主要 GUI 宿主提升，而不是扩展成重型工具链大里程碑。
- 本规范中的“基础能力基线”和“延后能力区域”就是后续规划的范围边界。

## 假设

- 当前优先级是“让编辑器更有意义地可用”，而不是“补齐所有高级编辑器能力”。
- 围绕项目、场景、面板、视口、选择和反馈建立更强的基础面，会在这个阶段创造最大价值。
- 未来高级能力将在当前基础面之上演进，而不是整体替换它。

## 范围外

- 与成熟引擎等价的完整内容浏览器
- 高级资产流水线创作能力
- 插件市场或包生态 UX
- 高级启动器生态能力
- 深度多文档编辑与协作系统

## 验收清单

- [x] 规范定义的是“更强的编辑器基础面”，而不是模糊的编辑器打磨目标
- [x] 用户故事聚焦用户价值，而不是实现方式
- [x] 验收标准基于可观察的用户行为与编辑器状态
- [x] 扩展性被表达为产品要求，而不是实现预设
- [x] 高级工具链诉求被明确留在当前里程碑之外
