# 原始笔记: 引擎上层开发 Roadmap

## 上下文
- 项目: HuaEngine
- 当前形态: 基于 C++17 / OpenGL / GLFW / GLAD / EnTT / ImGui 的游戏引擎原型，已有 Core、ECS、Scene、Rendering、Serialization、Reflection、Editor、Sandbox 等模块骨架
- 当前优先级来自用户说明: 先保证引擎基本功能可用（资产管理、序列化/反序列化、脚本继承），后续重心再转向渲染能力
- 明确约束: 目前不追求非常完善的工具链，不以复杂编辑器生态和完整生产管线为阶段目标

## 利益相关者
- 引擎维护者: 需要一张上层 roadmap，用来决定开发顺序、阶段目标和取舍
- 引擎模块开发者: 需要明确每个阶段先交付什么能力、什么不做
- 未来使用引擎做游戏/演示的开发者: 需要稳定的核心能力与逐步增强的渲染能力
- Editor / Sandbox 使用者: 需要可验证、可演示当前阶段能力的最小工作流

## 原始需求
### 功能性需求
- 形成一张面向当前引擎的上层开发 roadmap
- roadmap 需要体现分阶段目标，而不是零散任务清单
- roadmap 需要先覆盖基本引擎能力: 资产管理、序列化/反序列化、脚本继承
- roadmap 需要在基本能力之后，把渲染能力作为后续重点方向
- roadmap 需要能在上层指导开发取舍与优先级，不陷入过早做工具链
- roadmap 需要明确每一阶段的完成标志，便于判断是否进入下一阶段

### 非功能性需求
- roadmap 要清晰、可执行、可审查
- roadmap 要能反映“模块化、扩展性强”的长期目标
- roadmap 需要避免技术实现细节，保持 WHAT 层次
- roadmap 需要明确范围外事项，避免阶段蔓延

### 约束条件
- 现有引擎代码库为唯一上下文基础
- 当前阶段不以“非常完善的工具链”为目标
- 当前阶段允许 editor / sandbox 作为验证工具，但不要求完整生产力工具生态
- 开发重心顺序已由用户给定: 基础能力先于渲染深化

## 当前状态判断
- Core runtime、Editor workbench、ECS/Scene、Rendering、Serialization/Reflection 已有原型和骨架
- 资产管理尚未形成清晰的用户级工作流与阶段目标定义
- Scene / Material / Mesh 有部分序列化基础，但缺少上层 roadmap 对“什么时候算可用”的统一标准
- 脚本继承能力在接口层有痕迹，但未形成明确阶段目标与用户承诺
- 渲染模块已有主路径，但在用户目标中应放在基础能力稳定之后增强
