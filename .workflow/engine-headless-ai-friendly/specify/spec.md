## 1. 概述

为 HuaEngine 定义一套“GUI 可选、命令行可用、对 AI 代理友好”的统一操作面，使引擎核心能力在无图形工作台的情况下也能被创建、修改、验证和驱动。

**目标用户**: 引擎维护者、AI 代理/自动化脚本作者、游戏或内容开发者、Editor 用户

**成功指标**:
- 当前重点能力中，至少“项目/场景/资产/脚本/验证”这 5 类操作都存在非 GUI 可用路径
- 非交互调用能够返回稳定、机器可读、可据此继续自动化决策的结果
- GUI 被定义为可选客户端，而不是唯一操作入口

### 1.1 当前必须覆盖的最小无 GUI 范围

本规范当前要求无 GUI 操作面至少覆盖以下 5 类能力主题：

- Project: 项目初始化、项目上下文切换/识别、项目状态检查或校验
- Scene: 场景创建、读取、修改、保存、验证
- Asset: 资产登记、查询、校验或处理触发
- Script: 脚本挂接关系、脚本状态检查、脚本相关验证
- Validation: 针对当前重点能力的检查、执行结果与状态判断

## 2. 问题陈述

### 2.1 当前状态
HuaEngine 已具备 Core、Scene、Serialization、Rendering、Editor、Sandbox 等模块骨架，但很多可见操作仍主要依附于 Editor、Scene 面板、Inspector、Console 或 demo scene 初始化路径。当前操作面更接近“通过 GUI 或代码内嵌路径驱动引擎”，而不是“像 git / p4 那样，通过统一命令式接口操作引擎”。

### 2.2 痛点
- 当前许多能力的消费路径仍偏向 GUI 面板或 demo scene，导致无 GUI 环境下可操作性不足
- AI 代理和脚本系统缺少一个稳定、非交互、可组合的控制面，难以可靠驱动引擎能力
- 现有操作结果缺少统一的机器可读反馈口径，不利于自动化链路继续决策
- GUI 与核心能力的耦合过高时，会让 Editor 变成事实上的唯一入口，削弱引擎的可组合性和自动化价值

### 2.3 期望结果
形成一套新的上层规范：引擎核心操作必须能脱离 GUI 被执行，GUI 只作为可选客户端存在；AI 代理、脚本、CI 和本地开发者都能通过一致、可脚本化、可解析的操作面驱动引擎。

**验收标准**:

- [ ] AC-1.2: 当前重点能力中的场景、资产、脚本和验证操作都存在无 GUI 可用路径
- [ ] AC-1.3: 无 GUI 模式被定义为正式支持的使用方式，而不是临时调试通道
- [ ] AC-1.4: GUI 不再被描述为唯一或必经的入口

**备注**: 这里关注“可脱离 GUI 使用”，不规定具体命令形态。

### US-2: 让 AI 代理能够稳定驱动引擎

**优先级**: Must

```
作为 AI 代理或自动化脚本作者，
我想要通过稳定的非交互操作面驱动引擎能力，
以便我能持续执行、组合和判断下一步动作。
```

**验收标准**:
- [ ] AC-2.1: 非交互调用不会依赖人工点击、窗口焦点或 GUI 状态
- [ ] AC-2.2: 每次调用都能返回 AI 可据此继续决策的明确结果
- [ ] AC-2.3: 同一操作在重复调用时具有稳定的输入/输出语义
- [ ] AC-2.4: 失败结果能够清楚区分“输入问题”“状态问题”或“执行失败”这类不同原因

**备注**: 这里定义的是 AI 代理可消费性，不涉及具体协议或数据格式。

**优先级**: Must

```
作为游戏或内容开发者，
```

**验收标准**:

- [ ] AC-3.2: 资产相关的登记、查询、校验或处理存在非 GUI 可用路径
- [ ] AC-3.3: 这些操作能够在本地终端和自动化环境中以同样方式触发
- [ ] AC-3.4: 执行结果不会要求用户回到 GUI 中才能确认是否成功

**备注**: 此故事强调内容操作不再被 GUI 独占。

### US-4: 让脚本与验证能力进入 headless 工作流

**优先级**: Should

```
作为引擎维护者，
我想要让脚本能力和验证能力也进入 headless 工作流，
以便基础能力建设、自动测试和 AI 代理调度可以用同一套操作面完成。
```

**验收标准**:
- [ ] AC-4.1: 脚本相关操作不要求依赖 GUI 才能挂接、触发或验证
- [ ] AC-4.2: 基础验证操作可在无 GUI 模式下执行并给出明确结果
- [ ] AC-4.3: 无 GUI 验证结果能够用于判断当前能力是否可继续进入下一步
- [ ] AC-4.4: GUI 验证与 headless 验证在结果表达上不出现根本性分叉

**备注**: 这里关注“统一工作流”，不是具体测试方案。

```
作为 Editor 用户，

```

**验收标准**:
- [ ] AC-5.1: GUI 被描述为核心操作面的一个消费方，而不是唯一来源
- [ ] AC-5.2: GUI 与无 GUI 路径对同类能力的结果表达保持一致口径
- [ ] AC-5.3: 关闭 GUI 不会使核心引擎能力失去正式可用性
- [ ] AC-5.4: GUI 的存在被定义为效率层或体验层，而不是功能存在前提

**备注**: 这里定义 GUI 的定位变化，不涉及具体界面设计。
